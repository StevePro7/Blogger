# Chapter 25 — Class Metaprogramming

## 🧠 The big idea

Normally, you write:

```python
class Movie:
    ...
```

and Python creates the class for you.

**Class metaprogramming** is about customizing that process.

Instead of merely creating *instances* dynamically, you can make Python:

> **modify, enhance, or even construct classes automatically.**

The chapter presents a progression of techniques:

```text
Class
  ↓
class factory
  ↓
__init_subclass__
  ↓
class decorator
  ↓
metaclass
  ↓
__prepare__
```

The key lesson is **not** "use metaclasses everywhere."

It's almost the opposite:

> Use the **simplest class-building technique that solves the problem**. Metaclasses are the deepest and most powerful option, and are usually needed only in framework/library-level code. 

---

# 1. Classes are objects

This is the foundation of the chapter.

You already know:

```python
class Person:
    pass
```

creates a class.

But the class itself is also an **object**.

For example:

```python
Person.__class__
```

returns:

```text
<class 'type'>
```

So:

```text
Person
  ↓
is an instance of
  ↓
type
```

The book emphasizes that most Python classes are instances of `type`. Even `type` itself is an instance of `type`, avoiding an infinite regress. 

### Mental model

There are two levels:

```text
OBJECT LEVEL
    ↓
instances of classes

CLASS LEVEL
    ↓
classes are objects created by a metaclass
```

This distinction becomes extremely important when understanding metaclasses.

---

# 2. `type` is a class factory

You've probably used:

```python
type(obj)
```

to ask:

> "What class is this object?"

But `type` has another role.

You can use it to **create classes dynamically**.

Conceptually:

```python
type(name, bases, namespace)
```

For example:

```python
Dog = type(
    "Dog",
    (),
    {
        "speak": lambda self: "woof"
    }
)
```

is roughly equivalent to:

```python
class Dog:
    def speak(self):
        return "woof"
```

So:

```text
type
 ↓
creates
 ↓
class object
```

This is why the book calls `type` the **built-in class factory**.

---

# 3. Class factory functions

Before reaching metaclasses, the book demonstrates a simpler approach:

> Write a normal function that creates and returns a class.

For example, conceptually:

```python
def record_factory(...):
    ...
    return type(...)
```

This can be useful when you want to create many similar classes dynamically.

The important lesson is:

> **You don't need a metaclass just because you're dynamically creating classes.**

A class factory function may be enough.

This is part of the chapter's general philosophy: move toward more sophisticated metaprogramming only when simpler techniques aren't sufficient. 

---

# 4. `__init_subclass__`

This is probably the **most useful modern feature in the chapter**.

Suppose you have:

```python
class Checked:
    def __init_subclass__(cls):
        ...
```

Whenever someone creates:

```python
class Movie(Checked):
    ...
```

Python automatically calls:

```python
Checked.__init_subclass__(Movie)
```

So a base class can automatically customize its subclasses.

### Think of it as:

```text
Someone creates a subclass
          ↓
__init_subclass__ runs
          ↓
base class modifies/configures subclass
```

The chapter uses this to create a `Checked` base class that turns annotations such as:

```python
class Movie(Checked):
    title: str
    year: int
```

into runtime-checked fields using descriptor objects.

So subclasses get extra behavior **without having to implement it themselves**. 

---

# 5. `__init_subclass__` is a simpler alternative to metaclasses

This is a major takeaway.

Historically, people often used metaclasses to customize subclasses.

Python now provides:

```python
__init_subclass__
```

for many of those use cases.

So instead of:

```text
"I need a metaclass!"
```

ask:

```text
"Can __init_subclass__ solve this?"
```

The book presents `__init_subclass__` as a simpler modern mechanism for customizing subclasses. 

---

# 6. But `__init_subclass__` has a limitation

Here's an important technical detail.

`__init_subclass__` runs **after the class has already been created**.

That means:

```text
class body
   ↓
type.__new__
   ↓
class exists
   ↓
__init_subclass__
```

Therefore, it is too late to configure certain things that must be supplied during class creation.

The chapter's main example is:

```python
__slots__
```

Adding:

```python
__slots__ = ...
```

after the class has already been created doesn't have the desired effect.

So:

> If you need to control the namespace passed into `type.__new__`, `__init_subclass__` is too late.



This limitation is what eventually motivates the metaclass.

---

# 7. Class decorators

Another way to customize classes is a **class decorator**.

For example:

```python
@checked
class Movie:
    title: str
    year: int
```

The decorator receives the class:

```python
checked(Movie)
```

and returns a class that replaces the original binding.

Conceptually:

```text
class Movie
     ↓
created normally
     ↓
@checked
     ↓
Movie modified/replaced
```

The chapter uses a class decorator to implement essentially the same functionality as its `Checked` base class. 

---

# 8. `__init_subclass__` vs class decorator

Both can enhance an existing class.

### `__init_subclass__`

```python
class Checked:
    def __init_subclass__(cls):
        ...
```

Used by:

```python
class Movie(Checked):
    ...
```

### Class decorator

```python
@checked
class Movie:
    ...
```

### A useful difference

The book notes that a class decorator can sometimes be preferable when you don't want to interfere with **inheritance or metaclass relationships**. 

So:

```text
Need subclasses to automatically gain behavior?
        ↓
__init_subclass__

Need to modify one particular class?
        ↓
class decorator
```

That's a useful rule of thumb.

---

# 9. Import time vs runtime

This is one of the more subtle sections.

The book wants you to understand **when** all this metaprogramming happens.

Consider:

```python
@deco
class Klass(Base):
    attr = Descriptor()
```

A lot happens **before you ever instantiate `Klass`**.

The chapter's experiment demonstrates roughly this order:

```text
1. Execute class body
        ↓
2. Create descriptor instances
        ↓
3. type.__new__ creates the class
        ↓
4. __set_name__ runs on descriptors
        ↓
5. __init_subclass__ runs
        ↓
6. class decorator runs
        ↓
7. class becomes available under its name
        ↓
8. Later, an instance may be created
```

The book emphasizes that simply **importing the module** can trigger all of this. No instance needs to exist. 

### Why this matters

Metaprogramming often happens at:

> **class definition/import time**, not object runtime.

That's why framework code can "magically" configure classes before your application actually creates any objects.

---

# 10. Metaclasses

Now we reach the main subject.

A **metaclass is a class whose instances are classes**.

Normally:

```text
type
 ↓
creates
 ↓
MyClass
 ↓
creates
 ↓
my_object
```

More explicitly:

```text
type
  │
  └── creates → MyClass
                    │
                    └── creates → my_object
```

So:

```python
MyClass.__class__
```

is normally:

```python
type
```

A custom metaclass changes that:

```python
class Meta(type):
    ...
```

then:

```python
class MyClass(metaclass=Meta):
    ...
```

Now:

```text
Meta
 ↓
creates
 ↓
MyClass
 ↓
creates
 ↓
my_object
```



---

# 11. A metaclass is a "class factory"

This is the simplest definition to remember:

> **A metaclass is a class factory written as a class.**

Compare:

### Function-based class factory

```python
def make_class(...):
    return type(...)
```

### Metaclass

```python
class Meta(type):
    def __new__(meta_cls, name, bases, namespace):
        ...
        return super().__new__(...)
```

Both can customize class creation.

The metaclass is more deeply integrated into Python's class-building machinery.

---

# 12. `Meta.__new__`

The key metaclass method is:

```python
def __new__(meta_cls, name, bases, namespace):
    ...
```

It gets a chance to modify the class **before the final class object is created**.

This is much earlier than:

```python
__init_subclass__
```

or:

```python
@decorator
```

That's why metaclasses can do things those mechanisms cannot.

The book specifically uses metaclasses to dynamically configure `__slots__`, because that information must be present in the namespace passed to `type.__new__`. 

---

# 13. `__prepare__` — even earlier

The deepest level in the chapter is:

```python
__prepare__
```

A metaclass can define:

```python
@classmethod
def __prepare__(meta_cls, name, bases):
    ...
```

This is called **before the class body is executed**.

Its job is to provide the mapping that becomes the class namespace.

Conceptually:

```text
metaclass.__prepare__()
          ↓
namespace created
          ↓
class body executes inside namespace
          ↓
metaclass.__new__()
          ↓
class created
```

This gives you an extremely early opportunity to influence class creation. 

---

# 14. Why would anyone want `__prepare__`?

The chapter's `AutoConst` example demonstrates a clever use.

Normally:

```python
class Color:
    RED = 1
    GREEN = 2
    BLUE = 3
```

requires manually assigning values.

With a custom mapping returned by `__prepare__`, missing names can automatically receive values.

So:

```text
class body
   ↓
writes names into special mapping
   ↓
mapping's __missing__ handles unknown names
   ↓
automatic values generated
```

The book calls this a **metaclass hack**, demonstrating how powerful `__prepare__` can be. 

---

# 15. The complete class-creation sequence

This is **the most important thing to understand from the chapter**.

A simplified version is:

```text
class Movie(Base, metaclass=Meta):
    x = Descriptor()

    ↓

1. Determine the metaclass
        ↓
2. Meta.__prepare__()
        ↓
3. Execute the class body
        ↓
4. Meta.__new__()
        ↓
5. type.__new__()
        ↓
6. __set_name__ on descriptors
        ↓
7. __init_subclass__ on the base class
        ↓
8. class decorator is applied
        ↓
9. final class is bound to Movie
```

The chapter's evaluation experiments specifically demonstrate the relative timing of `__prepare__`, `__new__`, `__set_name__`, `__init_subclass__`, and class decorators. 

---

# ⭐ 16. The hierarchy of metaprogramming tools

This is probably the most useful practical summary of the chapter.

Think of these tools as increasing levels of power:

```text
                 SIMPLE
                   │
                   ↓
            Class decorator
                   │
                   ↓
          __init_subclass__
                   │
                   ↓
            class factory
                   │
                   ↓
              metaclass
                   │
                   ↓
              __prepare__
                   │
                   ↓
                 DEEP
```

But don't interpret this as "always use the highest one."

Quite the opposite:

> **Use the least powerful mechanism that solves the problem.**

The book repeatedly emphasizes that metaclasses are powerful but generally unnecessary for ordinary application code. 

---

# 17. Metaclass conflicts

One practical problem with metaclasses:

> **A class can only have one metaclass.**

Suppose:

```python
class MetaA(type):
    ...

class MetaB(type):
    ...
```

and you try:

```python
class MyClass(BaseA, BaseB):
    ...
```

where `BaseA` and `BaseB` require incompatible metaclasses.

Python can encounter a **metaclass conflict**.

This is one reason metaclasses can make class hierarchies difficult to compose.

The chapter explicitly lists:

> "A Class Can Only Have One Metaclass"

as an important practical consideration. 

---

# 18. Metaclasses should usually be implementation details

This is another excellent practical lesson.

Ideally, a user of your framework shouldn't have to think:

```python
class MyClass(metaclass=SomeCrazyMeta):
```

They should simply use:

```python
class MyClass(Base):
    ...
```

and let the framework handle the metaclass internally.

The chapter recommends treating metaclasses as **implementation details** whenever possible. 

---

# 19. Where class metaprogramming is useful

The chapter identifies several real-world applications:

* structural validation
* automatically applying decorators to many methods
* serialization
* object-relational mapping (ORM)
* persistence
* implementing special methods
* traits and aspect-oriented programming
* moving work to import/class-creation time for performance



This explains why frameworks can appear "magical."

They may be using:

```text
descriptors
+
class decorators
+
__init_subclass__
+
metaclasses
```

to automatically build the classes you use.

# 20. The `Checked` example ties the whole chapter together

The chapter progressively builds a class-building system.

Start with:

```python
class Movie:
    title: str
    year: int
```

The goal is to turn those annotations into runtime-checked fields.

The chapter explores several approaches:

```text
Checked base class
       ↓
__init_subclass__
       ↓
class decorator
       ↓
metaclass
```

The final metaclass-based version can do something the earlier versions cannot:

> **configure `__slots__` while the class is being created.**

This is an excellent demonstration of *why* metaclasses exist rather than simply being an abstract discussion. 

---

# 21. Why `__slots__` is important in this chapter

You encountered `__slots__` earlier in the book, but here it becomes a test of **when** class customization occurs.

`__slots__` must be part of the class namespace **before `type.__new__` creates the class**.

Therefore:

```text
__init_subclass__
       ❌ too late

class decorator
       ❌ even later

metaclass __new__
       ✅ early enough
```



This is one of the clearest reasons to understand class-creation timing.

After Chapters 23 and 24, you should see a progression:

You customize:


You customize:

# 🧠 The 10 things I would memorize

If you're studying this chapter, focus on these:

### 1. Classes are objects

```python
MyClass.__class__
# usually type
```

### 2. `type` is normally the metaclass

It creates most Python classes.

### 3. `type()` can create classes

```python
type(name, bases, namespace)
```

### 4. A class factory is just a function that builds classes

You don't necessarily need a metaclass.

### 5. `__init_subclass__`

Automatically runs when a subclass is created.

```python
class Base:
    def __init_subclass__(cls):
        ...
```

### 6. Class decorators

Receive a class and return a class:

```python
@decorator
class MyClass:
    ...
```

### 7. `__init_subclass__` and decorators operate after class creation

Therefore they cannot dynamically configure `__slots__`.

### 8. Metaclasses create classes

```python
class Meta(type):
    ...
```

and:

```python
class MyClass(metaclass=Meta):
    ...
```

### 9. `__prepare__` happens very early

It provides the namespace used while the class body executes.

### 10. Metaclasses are powerful but should be rare

Use simpler mechanisms whenever possible. The book's closing advice strongly favors straightforward code over unnecessary metaprogramming.

## ⭐ One-sentence takeaway

> **Chapter 25 teaches you that classes themselves are objects, and Python gives you progressively more powerful tools—class factories, `__init_subclass__`, class decorators, and finally metaclasses/`__prepare__`—to customize how those class objects are created.**
