# Chapter 23 — Consolidated Summary

## 1. Dynamic attributes: turning data into convenient objects

The chapter begins with a practical problem: **JSON data is usually just nested dictionaries and lists**, which can become unpleasant to work with:

```python
data["Schedule"]["events"][0]["name"]
```

The book shows how dynamic attributes can make this more natural:

```python
data.Schedule.events[0].name
```

The main example is **`FrozenJSON`**, which converts nested dictionaries into objects whose keys can be accessed as attributes.

The key mechanism is:

```python
def __getattr__(self, name):
    ...
```

`__getattr__` is called when normal attribute lookup **fails**, allowing the class to create a "virtual attribute" on demand. 

### Important distinction

```python
obj.name
```

normally looks for `name`.

If it cannot find it, Python can call:

```python
obj.__getattr__("name")
```

So `__getattr__` is excellent for **dynamic/fallback attributes**.

---

# 2. `__getattr__` vs `__getattribute__`

This is one of the most important concepts in the chapter.

### `__getattr__`

Called **only when normal attribute lookup fails**.

```python
class Demo:
    def __getattr__(self, name):
        return f"You asked for {name}"
```

Then:

```python
d = Demo()

d.foo
# "You asked for foo"
```

### `__getattribute__`

Called for **almost every attribute access**.

Conceptually:

```python
d.foo
```

causes something like:

```python
d.__getattribute__("foo")
```

If that eventually raises `AttributeError`, Python may then invoke `__getattr__`. 

### Easy way to remember

| Method             | When it runs                             |
| ------------------ | ---------------------------------------- |
| `__getattr__`      | "I couldn't find it — what should I do?" |
| `__getattribute__` | "Someone is asking for an attribute."    |

**Practical advice from the chapter:** `__getattribute__` and `__setattr__` are much easier to get wrong because they affect practically every attribute access. Properties/descriptors are generally less error-prone. 

---

# 3. `__new__`: flexible object creation

The `FrozenJSON` example eventually evolves to use:

```python
__new__
```

This is interesting because `__new__` controls **what object gets created**, before `__init__` runs.

The book uses it to make `FrozenJSON` act more like a **flexible factory**.

Depending on the input, the constructor can return:

* a `FrozenJSON` object
* a list
* or another appropriate object

So:

```python
FrozenJSON(data)
```

doesn't necessarily mean "create a `FrozenJSON` instance."

That's a deeper Python idea:

> **A class call does not necessarily have to produce an instance of that class.**

The chapter uses this to make the JSON conversion more elegant. 

---

# 4. The "bunch" idiom — creating attributes dynamically

Another useful technique is:

```python
self.__dict__.update(**kwargs)
```

Suppose:

```python
record = Record(
    name="Python",
    year=2026,
    location="Ireland"
)
```

The constructor can essentially turn the keyword arguments into attributes:

```python
record.name
record.year
record.location
```

The book calls this the **"bunch" idiom**.

It's useful when dealing with semi-structured data where you don't necessarily know all the fields ahead of time. 

### But there is a danger

If arbitrary external data becomes attribute names, those names could potentially **shadow methods or other attributes**.

The book specifically warns about this when dynamically creating many attributes from uncontrolled data. 

---

# 5. Properties: the central idea

This is probably the **most important part of the chapter**.

A property allows you to make something *look like a normal attribute* while actually executing code.

For example:

```python
class Circle:
    def __init__(self, radius):
        self.radius = radius

    @property
    def area(self):
        return 3.14 * self.radius ** 2
```

You use it like:

```python
circle.area
```

not:

```python
circle.area()
```

Yet `area` is actually being computed.

The chapter connects this to the **Uniform Access Principle**:

> Code using an object shouldn't need to know whether an attribute is stored data or computed data.

So you can initially expose:

```python
obj.price
```

as a normal attribute and later change the implementation to calculate it through a property **without changing the public interface**. 

---

# 6. Properties can have getter, setter, and deleter

A property can control three operations:

```python
@property
def weight(self):
    ...

@weight.setter
def weight(self, value):
    ...

@weight.deleter
def weight(self):
    ...
```

So:

```python
item.weight       # getter
item.weight = 10 # setter
del item.weight   # deleter
```

This is extremely useful for **encapsulation and validation**.

---

# 7. Properties for validation

The chapter's `LineItem` example demonstrates an important real-world use.

Suppose an item cannot have:

```python
weight <= 0
```

Instead of allowing:

```python
item.weight = -5
```

you can use a property:

```python
@property
def weight(self):
    return self.__weight

@weight.setter
def weight(self, value):
    if value <= 0:
        raise ValueError("weight must be > 0")
    self.__weight = value
```

Now the attribute still looks simple:

```python
item.weight = 10
```

but the setter enforces your business rule.

The book specifically uses properties to prevent invalid weight values and later generalizes the technique to price as well. 

### Key lesson

**Properties are a clean way to add validation without changing how users interact with your class.**

---

# 8. Properties can compute relationships between objects

The `Event` example is especially useful.

The JSON dataset contains things like:

```text
event
 ├── venue_serial = 1449
 └── speakers = [3471, 5199]
```

Instead of forcing the user to manually find those records, the class provides:

```python
event.venue
event.speakers
```

These are **computed properties** that automatically retrieve the related records.

So properties aren't only for validation.

They can also be used to create **convenient object relationships**.

The book describes this as "dereferencing" the serial numbers. 

---

# 9. Computed properties and caching

Here's an important practical issue.

Imagine:

```python
event.venue
```

requires a database query or API request every time.

You don't want:

```python
event.venue
event.venue
event.venue
```

to perform the expensive operation three times.

So the chapter discusses **caching computed properties**.

The progression is roughly:

### Approach 1 — manual caching

Compute once and store the result.

### Approach 2 — `@cached_property`

Python 3.8 introduced:

```python
@functools.cached_property
```

which caches the result in the instance attribute with the same name. 

### Approach 3 — `@property` + `@cache`

The second edition discusses both:

```python
@cached_property
```

and:

```python
@property
@functools.cache
def ...
```

because they have different semantics and trade-offs. 

### The important conceptual point

A property doesn't necessarily mean:

> "calculate this every time."

It can mean:

> "give me this value through attribute syntax."

That value might be calculated once and cached.

---

# 10. A subtle but VERY important point: properties override instance attributes

This is one of the chapter's deeper Python concepts.

Suppose you have:

```python
class Item:
    @property
    def price(self):
        return 100
```

and someone tries:

```python
item.__dict__["price"] = 500
```

The property can still control:

```python
item.price
```

because a property is an **overriding descriptor**.

This becomes important in Chapter 24, where descriptors are studied in depth. The chapter explicitly notes that properties are overriding descriptors and therefore aren't shadowed by ordinary instance attributes. 

This is one of the bridges between **Chapter 23 → Chapter 24**.

---

# 11. Property factory: avoiding repetitive code

Suppose you need identical validation for:

```python
weight
price
```

You don't want to write:

```python
@property
def weight(...)

@weight.setter
def weight(...)

@property
def price(...)

@price.setter
def price(...)
```

with almost identical logic.

The chapter introduces a **property factory**.

The idea is:

```text
property factory
       ↓
creates properties
       ↓
with common validation logic
       ↓
for multiple attributes
```

This uses an important combination of Python concepts:

* functions
* closures
* properties
* instance attributes
* descriptor behavior

The book describes this as an elegant generic solution that avoids duplicating the getter/setter code.

# 12. Attribute-handling tools you should know

The chapter finishes by bringing together the major mechanisms involved in attribute handling.

### Special attributes

Particularly important:

```python
__dict__
__class__
```

### Built-in functions

Know:

```python
getattr()
setattr()
hasattr()
delattr()
dir()
```

For example:

```python
getattr(obj, "name")
```

is roughly the dynamic equivalent of:

```python
obj.name
```

while:

```python
setattr(obj, "name", value)
```

is equivalent to:

```python
obj.name = value
```

---

# 13. Special methods for attribute handling

You should know these four especially well:

```python
__getattr__
__getattribute__
__setattr__
__delattr__
```

Conceptually:

```text
obj.name
   ↓
__getattribute__
   ↓
normal lookup fails?
   ↓
__getattr__
```

And:

```text
obj.name = value
       ↓
__setattr__
```

And:

```text
del obj.name
       ↓
__delattr__
```

The chapter also discusses:

```python
__dir__
```

for controlling what appears when `dir(obj)` is called.

# 🧠 What I would memorize for an exam/interview

If you're studying this chapter, I'd focus on these **10 points**:

1. **Dynamic attributes** can be created or computed at runtime.
2. `__getattr__` is called **only when normal lookup fails**.
3. `__getattribute__` participates in **every normal attribute lookup**.
4. `__setattr__` intercepts attribute assignment.
5. `__new__` controls **object creation** and can return objects other than instances of the class.
6. A **property** makes a method behave like an attribute.
7. Properties allow **getters, setters, and deleters**.
8. Properties are excellent for **validation** and **computed values**.
9. Computed properties can be **cached**, using tools such as `functools.cached_property`.
10. **Properties are descriptors**, which is the key concept leading into Chapter 24. 

## One-sentence takeaway

**Chapter 23 teaches you how Python can make an attribute interface stay simple (`obj.price`) while the implementation behind that interface can be dynamic, computed, validated, cached, or otherwise controlled.**
