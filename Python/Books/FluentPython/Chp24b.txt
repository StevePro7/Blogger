# Chapter 24 — Attribute Descriptors

## 🧠 The big idea

A **descriptor** is an object that controls what happens when another object's attribute is accessed.

In simplified terms:

```text
You write:

item.price
item.price = 100
del item.price

        ↓

Python asks a descriptor:

"How should I handle this?"
```

A descriptor is a **class** implementing one or more of:

```python
__get__
__set__
__delete__
```

The book emphasizes that descriptors are a fundamental part of Python's object model. Properties, methods, `classmethod`, and `staticmethod` all rely on descriptor behavior. 

---

# 1. What exactly is a descriptor?

A descriptor is simply a class that implements the descriptor protocol:

```python
class MyDescriptor:
    def __get__(self, instance, owner):
        ...

    def __set__(self, instance, value):
        ...

    def __delete__(self, instance):
        ...
```

You then use an **instance of that descriptor as a class attribute**:

```python
class Product:
    price = MyDescriptor()
```

This is crucial.

### Don't confuse these two things

```python
class Product:
    price = MyDescriptor()
```

Here:

```text
Product.price
    ↓
descriptor object
```

But:

```python
p = Product()
p.price
```

causes the descriptor to manage access to `price` for `p`.

The book calls:

* **descriptor class** → the class implementing `__get__`, `__set__`, etc.
* **descriptor instance** → the object assigned to `Product.price`
* **managed class** → `Product`
* **managed instance** → `p`
* **storage attribute** → where the actual value is stored



---

# 2. The `LineItem` example

This is the main example of the chapter.

Imagine an order item:

```python
class LineItem:
    def __init__(self, description, weight, price):
        self.description = description
        self.weight = weight
        self.price = price
```

We want:

```python
weight > 0
price > 0
```

Chapter 23 used properties for this.

Chapter 24 says:

> Instead of creating separate properties, create a reusable **descriptor class**.

For example:

```python
class Quantity:
    def __set__(self, instance, value):
        if value <= 0:
            raise ValueError("value must be > 0")

        instance.__dict__[self.storage_name] = value
```

Then:

```python
class LineItem:
    weight = Quantity()
    price = Quantity()
```

Now the **same validation logic** manages both `weight` and `price`. 

### This is the major advantage of descriptors

Instead of:

```text
weight → property → validation
price  → property → validation
```

you can have:

```text
          ┌── Quantity ──→ weight
LineItem ─┤
          └── Quantity ──→ price
```

One reusable class manages multiple attributes.

---

# 3. VERY important: `self` vs `instance`

This is one of the easiest places to get confused.

Inside:

```python
class Quantity:
    def __set__(self, instance, value):
        ...
```

there are **two different objects**:

### `self`

The descriptor object:

```python
LineItem.weight
```

or:

```python
LineItem.price
```

### `instance`

The actual `LineItem` object:

```python
item = LineItem(...)
```

So:

```python
self
```

means:

> "Which descriptor am I?"

while:

```python
instance
```

means:

> "Which LineItem object am I managing?"

The book strongly warns that values should be stored in the **managed instance**, not in the descriptor itself. 

### Why?

Imagine you have:

```python
item1 = LineItem(...)
item2 = LineItem(...)
```

There may be thousands of `LineItem` instances, but only one descriptor object for:

```python
LineItem.weight
```

If the descriptor stored the value in itself, all `LineItem` instances could end up sharing that value.

Instead:

```python
instance.__dict__[self.storage_name] = value
```

stores the value in the individual object.

---

# 4. `__set_name__` — one of the most important features

Initially, the descriptor needs to know:

```text
Where should I store the value?
```

For example:

```python
class Quantity:
    def __init__(self, storage_name):
        self.storage_name = storage_name
```

Then:

```python
class LineItem:
    weight = Quantity("weight")
    price = Quantity("price")
```

But that's repetitive and error-prone.

You could accidentally write:

```python
price = Quantity("weight")
```

😬

Python 3.6 introduced:

```python
__set_name__
```

Now you can simply write:

```python
class Quantity:
    def __set_name__(self, owner, name):
        self.storage_name = name
```

and:

```python
class LineItem:
    weight = Quantity()
    price = Quantity()
```

Python automatically calls:

```python
descriptor.__set_name__(LineItem, "weight")
descriptor.__set_name__(LineItem, "price")
```

So the descriptor knows what attribute name it manages. 

### Memorize this

```python
def __set_name__(self, owner, name):
```

means roughly:

> "Python is telling this descriptor what name it was assigned to."

This dramatically simplifies descriptor implementations.

---

# 5. The descriptor protocol

The three key methods are:

```python
__get__
__set__
__delete__
```

Think of them as:

| Operation          | Descriptor method |
| ------------------ | ----------------- |
| `obj.attr`         | `__get__`         |
| `obj.attr = value` | `__set__`         |
| `del obj.attr`     | `__delete__`      |

Not every descriptor needs all three.

The book explicitly notes that **partial implementations are perfectly valid**. 

---

# 6. `__get__` has two important situations

A descriptor's:

```python
__get__(self, instance, owner)
```

receives:

* `self` → descriptor object
* `instance` → managed object
* `owner` → managed class

So:

```python
item.price
```

roughly results in:

```python
descriptor.__get__(item, LineItem)
```

But:

```python
LineItem.price
```

results in:

```python
descriptor.__get__(None, LineItem)
```

That `instance=None` behavior is important when designing descriptors. 

---

# 7. The BIG distinction: overriding vs non-overriding descriptors

This is probably the **most important concept in Chapter 24**.

There are two major types.

## A. Overriding descriptor

A descriptor that implements:

```python
__set__
```

is an **overriding descriptor**.

The official terminology is **data descriptor**.

It takes control over assignments to the managed attribute. 

For example:

```python
class Quantity:
    def __get__(self, instance, owner):
        ...

    def __set__(self, instance, value):
        ...
```

Then:

```python
item.price = 100
```

doesn't simply create:

```python
item.__dict__["price"] = 100
```

Instead, Python invokes:

```python
Quantity.__set__(...)
```

---

# 8. Non-overriding descriptor

If the descriptor does **not** implement `__set__`, it is a **non-overriding descriptor**.

Official terminology:

> **non-data descriptor**

Example:

```python
class Descriptor:
    def __get__(self, instance, owner):
        ...
```

Now an instance attribute with the same name can **shadow** the descriptor.

For example:

```python
class A:
    x = Descriptor()

a = A()

a.x = 10
```

Now:

```python
a.x
```

returns:

```text
10
```

rather than invoking the descriptor.

The instance attribute has shadowed the non-overriding descriptor. 

---

# ⭐ The easiest way to remember this

### Data / overriding descriptor

```python
__get__
__set__
```

**Descriptor wins.**

### Non-data / non-overriding descriptor

```python
__get__
```

**Instance attribute can win.**

Think:

```text
             Has __set__?
                 │
          ┌──────┴──────┐
          │             │
         YES            NO
          │             │
     overriding     non-overriding
      descriptor       descriptor
          │             │
      controls       instance
      attribute      can shadow it
```

This distinction is central to understanding Python attribute lookup.

# 9. What happens with `@property`?

Here's a beautiful connection to Chapter 23:

**A property is a descriptor.**

So when you write:

```python
class Circle:

    @property
    def area(self):
        return ...
```

Python creates a property object that implements the descriptor protocol.

That's why properties can control:

```python
circle.area
circle.area = ...
del circle.area
```

The book explicitly points out that properties are **overriding descriptors**. 

So:

```text
Chapter 23
    ↓
@property
    ↓
Chapter 24
    ↓
"How does @property actually work?"
    ↓
Descriptors
```

# 10. Methods are descriptors too 😮

This is another major insight.

Consider:

```python
class Dog:
    def bark(self):
        print("woof")
```

You write:

```python
dog.bark()
```

But `bark` is actually a function stored on the class.

Functions implement the descriptor protocol.

That's why:

```python
dog.bark
```

produces a **bound method** where `dog` has effectively been supplied as `self`.

The chapter therefore says:

> **Methods are descriptors.**

This is one of the reasons descriptors are so fundamental to Python. 

---

# 11. `cached_property` is a non-overriding descriptor

This connects directly to Chapter 23.

The book notes that:

```python
@functools.cached_property
```

creates a **non-overriding descriptor**.

Why is that useful?

Initially:

```python
obj.expensive_value
```

runs the descriptor and calculates the value.

Then the result is stored as an instance attribute:

```python
obj.__dict__["expensive_value"] = result
```

Next time:

```python
obj.expensive_value
```

the instance attribute shadows the descriptor.

So the expensive calculation doesn't happen again. 

This is an excellent example of why the overriding/non-overriding distinction matters.

---

# 12. Methods can also be shadowed

Because ordinary methods are non-overriding descriptors, you can technically do:

```python
obj.method = 7
```

Then:

```python
obj.method
```

returns:

```python
7
```

rather than the method.

This only affects that particular instance.

The class method itself remains intact.

The chapter also points out that this doesn't work the same way for **special methods**, because Python looks those up on the class rather than through the instance. 

---

# 13. A descriptor can be used for validation

The chapter develops a reusable architecture:

```python
class Validated:
    def __set_name__(self, owner, name):
        self.storage_name = name

    def __set__(self, instance, value):
        value = self.validate(self.storage_name, value)
        instance.__dict__[self.storage_name] = value

    def validate(self, name, value):
        raise NotImplementedError
```

Then specialized descriptors:

```python
class Quantity(Validated):
    def validate(self, name, value):
        if value <= 0:
            raise ValueError(...)
        return value
```

and:

```python
class NonBlank(Validated):
    def validate(self, name, value):
        value = value.strip()
        if not value:
            raise ValueError(...)
        return value
```

Now:

```python
class LineItem:
    description = NonBlank()
    weight = Quantity()
    price = Quantity()
```

This is much more powerful than writing separate validation properties. 

### Conceptually

```text
                 Validated
                    │
             ┌──────┴──────┐
             ↓             ↓
         Quantity       NonBlank
             │             │
             ↓             ↓
      weight / price   description
```

The common mechanism lives in the base descriptor.

Only the validation rule changes.

---

# 14. Why descriptors store data in the instance

This deserves repeating because it's a common beginner mistake.

❌ Wrong:

```python
self.__dict__[self.storage_name] = value
```

where `self` is the descriptor.

That would mean the value belongs to the **descriptor**, which is shared by all managed instances.

✅ Correct:

```python
instance.__dict__[self.storage_name] = value
```

Now each object has its own value.

```text
LineItem.weight descriptor
          │
          │ manages
          ├──── item1.weight
          ├──── item2.weight
          └──── item3.weight
```

Each `LineItem` owns its own actual data. 

---

# 15. Descriptors can be abstract and reusable

The chapter goes beyond one descriptor and shows how to build a general framework.

For example:

```python
class Validated(ABC):
    ...
```

provides the common machinery:

```text
__set_name__
__set__
storage
```

while subclasses provide:

```text
validate()
```

This is essentially a **template method / self-delegation** approach.

The important design lesson is:

> Put the repeated descriptor machinery in a base class and let subclasses define the specific validation behavior.



---

# 16. Descriptors can be overwritten on the class

A subtle but important point:

```python
class Managed:
    x = SomeDescriptor()
```

doesn't make the descriptor completely untouchable.

You can do:

```python
Managed.x = 42
```

and the descriptor is replaced.

After that:

```python
obj.x
```

will simply see `42`.

This is effectively a form of **monkey patching**.

The book demonstrates that both overriding and non-overriding descriptors can be replaced by assigning directly to the managed class. 

---

# 17. `__delete__`

Descriptors can also control deletion:

```python
def __delete__(self, instance):
    ...
```

which handles:

```python
del obj.attribute
```

The chapter closes by connecting this to properties: properties can manage deletion too, and descriptors can implement `__delete__` for the same purpose.
